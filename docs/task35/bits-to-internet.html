01 · Inside one byte

char and how a negative number looks in memory

A byte does not know it is negative. It holds eight bits. "Negative" is an agreement between you and the compiler about how to read those bits.

In C, char is one byte — 8 bits, so 256 possible patterns. The only question is what those 256 patterns mean:

TypeSizeRangePattern 1111 1011 means
unsigned char1 byte0 … 255251
signed char1 byte−128 … +127−5
char1 bytesigned or unsigned — implementation defineddepends on your compiler
Watch out

Plain char is signed on x86 Linux/macOS but unsigned on ARM Linux. If the sign matters to your code, say signed char or unsigned char explicitly. Never assume.

Two's complement, in three moves

To write −X in a byte: take the bit pattern of +X, flip every bit (one's complement), then add 1. That's it.

−5

derivation
  +5   =  0000 0101
  flip =  1111 1010   ← one's complement
  +1   =  1111 1011   ← two's complement = −5

  hex    = 0xFB
  read as unsigned char → 251

−15

derivation
  +15  =  0000 1111
  flip =  1111 0000
  +1   =  1111 0001   ← −15

  hex    = 0xF1
  read as unsigned char → 241

−128 — the interesting one

There is no +128 in a signed char. So do the procedure on the pattern for 128 anyway and watch what happens:

derivation
  128  =  1000 0000
  flip =  0111 1111
  +1   =  1000 0000   ← unchanged! −128 is its own two's complement

  hex    = 0x80
  read as unsigned char → 128

This is why the range is lopsided: −128 … +127, not −127 … +127. Zero takes up one of the "positive" slots, so there is one spare pattern at the negative end. In C, -(-128) in a signed char overflows back to −128.

Why flip-and-add-one, and not something simpler?

Because it makes subtraction free. The CPU's adder handles negatives with no extra circuitry — the carry out of the top bit is simply discarded:

5 + (−5) using ordinary binary addition
    0000 0101     5
  + 1111 1011    −5
  -----------
  1 0000 0000   carry out of bit 7 is dropped
    0000 0000   = 0  ✓

A sign-and-magnitude scheme would need a separate subtractor and would have two zeros (+0 and −0). Two's complement has exactly one zero and one adder. That economy is the whole reason it won.

The point of the exercise

Three lines of C produced three bytes: 0xFB, 0xF1, 0x80. Nothing in memory records "these are negative." The type in the source code is the only thing that decides whether bit 7 is a sign bit or just another power of two. Change the type, and the same byte becomes a different number.

Bitwise operators work on bits. Logical operators work on truth.

The single most common C bug in this course: writing & when you meant &&. They are not related operators that happen to look alike. They live in different worlds.

The six bitwise operators

Each one takes the operands apart into bits and works column by column. The result is a number.

OpNameRule, per bit columnTypical use
&AND1 only if both bits are 1Test or clear bits — masking
|OR1 if either bit is 1Set bits — combining flags
^XOR1 if the bits differToggle bits, find differences, swap
~NOT (unary)flip every bitBuild an inverted mask
<<left shiftslide bits left, feed in 0sMultiply by 2ⁿ, build a mask
>>right shiftslide bits rightDivide by 2ⁿ, extract a field

two examples

  int x = 5;

<< — left shift

two examples
Example 1 — 3 << 2

>> — right shift

two examples
Example 1 — 12 >> 2   (unsigned: 0s shift in — logical shift)
    0000 1100   12

Example 2 — extracting the 2nd byte of an IPv4 address
  ip = 192.168.1.25  →  0xC0A80119

Two shift traps

1. Right-shifting a negative signed value is implementation-defined; every real compiler does an arithmetic shift (copies the sign bit in), so -8 >> 1 gives −4, not 124. Shift unsigned values when you care about the bits.

2. Shifting by ≥ the width of the type is undefined behaviour. 1 << 32 on a 32-bit int is not 0 — it is a bug that may print anything.

The three logical operators

These treat each operand as a single truth value: 0 is false, anything else is true. The result is always 0 or 1 — never a bit pattern.

OpNameResultShort-circuits?
&&logical AND1 if both operands are non-zeroYes — skips the right side if left is 0
||logical OR1 if either operand is non-zeroYes — skips the right side if left is non-zero
!logical NOT1 if operand is 0, else 0n/a

&& — logical AND

two examples
Example 1 — a range check
  int age = 22;
  (age >= 18 && age < 60)   →  1 && 1  →  1   true

Example 2 — short-circuit saves you from a crash
  if (p != NULL && p->value > 0) { ... }
  if p is NULL, the left side is 0, so p->value is NEVER evaluated.
  Swap the order and the program segfaults.

|| — logical OR

two examples
Example 1
  int c = 'y';
  (c == 'y' || c == 'Y')   →  1 || 0  →  1

Example 2 — short-circuit avoids the expensive call
  if (cache_hit(key) || fetch_from_disk(key)) { ... }
  if cache_hit returns non-zero, fetch_from_disk is never called.

! — logical NOT

two examples
Example 1
  !0    →  1
  !12   →  0        12 is "true", so !12 is false
  !!12  →  1        the classic "normalise to 0 or 1" trick

Example 2 — the empty-string idiom
  if (!strcmp(a, b)) { ... }   strcmp returns 0 when equal,
                               so !0 = 1 = "the strings match"

The bug you will actually write

& vs && — same inputs, different worlds
  int a = 12, b = 10;

  a &  b   →  8      bitwise: 0000 1100 & 0000 1010 = 0000 1000
  a && b   →  1      logical: both are non-zero, so "true"

  And the one that silently passes your tests:
  int x = 1, y = 2;
  x &  y   →  0      0001 & 0010 = 0000  ← looks like "false"!
  x && y   →  1      both non-zero  ← the answer you wanted

x & y and x && y agree often enough that the bug survives testing and dies in production. Read your operators out loud: "bit-and" vs "and-and".

NAND: the one gate that everything is made of

Give me enough NAND gates and I will build you a computer. Not metaphorically — literally, and you will do it yourself in twelve projects.

The gate

NAND is "NOT AND": output is 1 unless both inputs are 1.

Functional completeness

A set of gates is functionally complete if every possible boolean function can be built from it alone. {AND, OR, NOT} is complete. So is {NAND} — all by itself. So is {NOR}. Nothing else you need exists outside what NAND can express.

Building the rest from NAND alone

the three constructions
NOT a       — feed the same signal into both inputs
  NOT a = NAND(a, a)
    a=0 → NAND(0,0) = 1  ✓
    a=1 → NAND(1,1) = 0  ✓

a AND b     — NAND then invert
  a AND b = NOT( NAND(a,b) )
          = NAND( NAND(a,b), NAND(a,b) )        2 NANDs

a OR b      — De Morgan: a OR b = NOT( NOT a AND NOT b )
  a OR b  = NAND( NOT a, NOT b )
          = NAND( NAND(a,a), NAND(b,b) )        3 NANDs

a XOR b     — 4 NANDs
  t = NAND(a, b)
  a XOR b = NAND( NAND(a, t), NAND(b, t) )

Why NAND and not AND?

Two reasons, and the second is the one that decided it.

  • Logical: NAND is universal, so a fab only needs to perfect one cell design and can compose everything else from it.
  • Physical: in CMOS, transistors naturally invert. A NAND gate is 4 transistors — 2 PMOS in parallel, 2 NMOS in series. A plain AND gate is a NAND plus an inverter: 6 transistors. Inverting logic is genuinely cheaper, smaller, and faster in silicon. The hardware wants to be NAND.

The connection back to sections 01–02

Section 01 said a byte is 8 bits and negatives are two's complement. Section 02 said &, |, ^, ~ act per column. Now you can see why those are the primitive operations of C: they are the operations the ALU physically has gates for. a & b is 8 AND gates side by side. a + b is a chain of full adders, each one a handful of NANDs. And two's complement is not a convention someone chose for elegance — it is the representation that lets the same adder circuit do subtraction, saving an entire second block of silicon.

The stack is: electrons → transistors → NAND → gates → adders/ALU → CPU → machine code → C → your program. You are working at layer 8. It is worth having seen layers 1–7 once.

One bit per pixel: bitmaps and masks

You want to replace the background behind a person in a photo. First question, before any code: how do you even write down "where the person is"?

Two ways to record the same fact

Take a 1920×1080 photo — 2,073,600 pixels. Suppose the person covers about 20% of the frame: roughly 414,720 pixels.

RepresentationWhat you storeSizeLookup "is pixel (i,j) the person?"
Coordinate list414,720 × (i,j) pairs, 2 bytes each≈ 1.66 MBSearch the list — O(n), or build a hash set
Byte mask1 byte per pixel, 0 or 255≈ 2.07 MBO(1) array index
Bitmap mask1 bit per pixel≈ 259 KBO(1) — index + shift + mask

The bitmap wins on both axes at once, and that is the interesting part. It is 6.5× smaller than the coordinate list and gives constant-time lookup, which the list cannot. Three things make this work:

  • Position is implicit. The list spends 4 bytes saying "pixel (734, 210)". The bitmap doesn't store the coordinate at all — the coordinate is the bit's position in the array. You get it for free.
  • The answer is one bit, so store one bit. "Person or background" is a yes/no question. Anything larger than 1 bit is wasted.
  • Fixed size, whatever the subject. The list grows with the person; the bitmap is 259 KB whether the person fills 5% or 95% of the frame. Predictable memory is easy to allocate and easy to cache.
When the list wins

If the region is tiny — say 500 pixels in a 4K image — the list is 2 KB and the bitmap is still 1 MB. Sparse data wants a list (or run-length encoding); dense data wants a bitmap. This is the same trade-off as adjacency list vs adjacency matrix in graphs, and sparse vs dense arrays. Learn to spot it: the crossover is roughly when the region exceeds 1/32 of the frame.

Packing bits into bytes

mask.c — one bit per pixel
/* width*height bits, rounded up to whole bytes */
unsigned char *mask = calloc((W * H + 7) / 8, 1);

static inline int idx(int i, int j) { return i * W + j; }

/* mark pixel (i,j) as foreground — SET the bit */
void set_px(unsigned char *m, int i, int j) {
    int n = idx(i, j);
    m[n / 8] |= (1u << (n % 8));          ← OR sets a bit
}

/* is pixel (i,j) foreground? — TEST the bit */
int get_px(const unsigned char *m, int i, int j) {
    int n = idx(i, j);
    return (m[n / 8] >> (n % 8)) & 1u;    ← shift down, AND off
}

/* clear it — AND with the inverse */
void clr_px(unsigned char *m, int i, int j) {
    int n = idx(i, j);
    m[n / 8] &= ~(1u << (n % 8));
}

Every operator in that file came from section 02. << builds the mask, |= sets, &=~ clears, >> and & test. This is what those operators are for.

Compositing: four operations, one image

Let M be the mask (1 = person). Then:

foreground = original AND M keeps the person, blacks out everything else inverse = NOT M 1 = background, 0 = person new_back = new_image AND (NOT M) keeps the new scene, blacks out a person-shaped hole final = foreground OR new_back the hole and the person fit together exactly

The OR works only because the two images are complementary — wherever one has real pixels the other has zeros, so there is never a collision. That is the whole trick. In practice you write it as a per-channel select:

composite.c
for (int i = 0; i < H; i++)
  for (int j = 0; j < W; j++) {
    int n = i * W + j;
    if (get_px(mask, i, j))
        out[n] = original[n];      /* person   */
    else
        out[n] = newbg[n];         /* backdrop */
  }
Simplification, stated on purpose

A real background-replacement pipeline does not use a hard 1-bit mask at the edges — hair and motion blur need an alpha matte, 8 bits per pixel, where out = α·person + (1−α)·backdrop. The 1-bit mask is the correct mental model and the correct starting implementation; alpha is the refinement. We are teaching the idea, not shipping Zoom.

From one byte to N bytes — the general rule

Everything in section 01 was about 8 bits. Nothing about it depended on the number 8.

The derivation

N bytes = 8N bits. Each bit has 2 states and the bits are independent, so the number of distinct patterns is

2 × 2 × 2 × … × 2 (8N times) = 2^(8N)

Unsigned. Use all 8N bits for magnitude. Patterns run from all-zeros to all-ones, mapped straight onto the integers starting at 0:

0 … 2^(8N) − 1 the −1 is because we started counting at 0, not 1

Signed (two's complement). Split the 2^(8N) patterns into two equal halves of 2^(8N−1) each:

  • Top bit 0 → non-negative. That half holds 0 … 2^(8N−1) − 1. There are 2^(8N−1) values, but one of them is spent on zero, so the largest positive is 2^(8N−1) − 1.
  • Top bit 1 → negative. That half holds −2^(8N−1) … −1. All 2^(8N−1) values are real negatives — zero is not repeated here.
−2^(8N−1) … +2^(8N−1) − 1 exactly 2^(8N) values, no gaps, no duplicates
Why the asymmetry, in one sentence

There are as many negative numbers as non-negative numbers, but "non-negative" has to include zero — so the positives are one short. That is the entire explanation for −128 … +127, −2147483648 … +2147483647, and every other lopsided range you will meet.

Three places this bites in real code

  • The 2038 problem. Unix time is seconds since 1970 in a signed 32-bit integer. It runs out at 2^31 − 1 seconds = 03:14:07 UTC on 19 January 2038, then wraps to −2^31 — the year 1901. The fix is a 64-bit time_t, which lasts about 292 billion years.
  • The IPv4 problem. 4 bytes = 2^32 ≈ 4.3 billion addresses. That number felt infinite in 1981. Section 06 is what happened next.
  • Signed/unsigned comparison. if (i < strlen(s)) where i is a negative int: C converts i to size_t, and −1 becomes 18,446,744,073,709,551,615. The loop does not terminate the way you expected. This is the same "same bits, different reading" idea from section 01, now costing you a production outage.

06 · Addresses

IPv4: four bytes, and what we did with 2³² of them

An IPv4 address is a 32-bit unsigned integer. The dots are punctuation for humans. The machine never sees them.

Why 2³²

Four bytes, each holding 0–255 (section 01), each independent of the others:

256 × 256 × 256 × 256 = (2⁸)⁴ = 2^(8×4) = 2³² = 4,294,967,296

That is exactly the "N = 4, unsigned" row of the table in section 05. Nothing new — just the general rule with N set to 4.

192.168.1.25 is one number
  192      .  168      .  1        .  25
  11000000 .  10101000 .  00000001 .  00011001

  as one 32-bit unsigned int:  11000000101010000000000100011001
  in hex:                      0xC0A80119
  in decimal:                  3232235801

This matters practically. Databases store IPs as a 4-byte integer, not a 15-character string — 4 bytes instead of 15, and range queries become integer comparisons. And extracting the third octet is just (ip >> 8) & 0xFF, straight out of section 02.

Not all 4.3 billion are usable

Broadcast, more carefully

There are two kinds and students routinely conflate them:

  • Limited broadcast — 255.255.255.255. "Everyone on my local link." Routers drop it. Used when you don't yet know your own subnet, which is precisely the DHCP situation.
  • Directed broadcast — the last address of a subnet, e.g. 192.168.1.255 for 192.168.1.0/24. Reaches everyone in that subnet. Routers almost always block it now, because it was the ammunition for the Smurf amplification attack.

So in a /24 subnet the first address (192.168.1.0, the network ID) and the last (192.168.1.255, broadcast) are not assignable. 256 addresses, 254 usable hosts.

Why the private ranges exist at all

They are the reason the Internet did not stop growing in 2005. There are roughly 4.3 billion IPv4 addresses and far more devices than that. RFC 1918 says: these three blocks are guaranteed never to be routed on the public Internet, so every network in the world may reuse them simultaneously. AI Karyashala uses 192.168.1.0/24. So does a house in Lisbon and an office in Nairobi. No conflict, because those addresses never appear in a packet on the open Internet — a router rewrites them on the way out. That rewriting is NAT, and it is section 09.

2¹²⁸ is not "four times bigger" than 2³². It is 2⁹⁶ times bigger — roughly 79 octillion times. It is enough to give every grain of sand on Earth its own /64 network several times over. The size was chosen so that address exhaustion never has to be solved again.

What IPv6 actually changes

Address space and structure

The standard LAN allocation is a /64 — 2⁶⁴ addresses on a single link, more than the entire IPv4 Internet squared. A home is typically delegated a /56 or /48 by the ISP, giving 256 or 65,536 separate /64 subnets. A college gets a /48 and can hand every classroom its own /64 without ever thinking about address budgets. Compare that with the careful subnet arithmetic in section 11 — it simply disappears.

Network configuration — SLAAC

A device joining an IPv6 network sends a Router Solicitation, gets back a Router Advertisement carrying the /64 prefix, and builds its own address by appending an interface identifier. No DHCP server required. The DORA exchange in section 12 becomes two messages, and works even on a network with no server at all. DHCPv6 still exists for when you want central control over DNS servers and address assignment.

Routing and scalability

IPv6 was allocated hierarchically from the start: a region gets a big block, an ISP gets a slice, a customer gets a slice of that. So an ISP advertises one aggregated prefix to the world instead of hundreds of fragmented IPv4 blocks accumulated over thirty years of trading. Smaller global routing tables, less router memory, faster convergence. Add the fixed 40-byte header with no checksum to recompute, and per-packet forwarding work drops at every hop.

Security capabilities

IPsec was designed as an integral part of the IPv6 architecture — the Authentication Header and Encapsulating Security Payload are native extension headers, not bolt-ons. Note the honest caveat: it was mandatory to implement in the original spec but was downgraded to recommended in RFC 6434, and it is not mandatory to use. In practice most traffic security today is TLS at the application layer regardless of IP version. The genuine IPv6 wins are architectural: no NAT means end-to-end integrity checks are meaningful again, and Secure Neighbor Discovery (SEND) can authenticate the address-resolution step that ARP leaves wide open.

There is a cost too, and you should say it out loud in class: a globally routable address on every device removes the accidental firewall that NAT provided. IPv6 networks need an explicit stateful firewall policy. And because a device's address once embedded its MAC address, privacy extensions (RFC 8981) were added to rotate the interface identifier so you cannot be tracked across networks by your address.

IoT and what comes next

A campus deploying a thousand sensors under IPv4 needs private addresses, a NAT gateway, and a way to reach each sensor from outside — which NAT actively prevents. Under IPv6 each sensor has a real address and is directly addressable, subject to firewall policy. This is why 6LoWPAN, Thread, and Matter — the low-power mesh protocols in smart-home devices — are all IPv6-based. Peer-to-peer applications, VoIP, and game networking also become dramatically simpler when both ends have real addresses and no NAT traversal hacks are required.

Also worth knowing

  • Neighbor Discovery Protocol replaces ARP, running over ICMPv6 and using multicast instead of broadcast — so a lookup disturbs only the machines that might answer, not every device on the link.
  • Multicast is structured. Addresses carry an explicit scope: link-local, site-local, global. ff02::1 is all nodes on this link.
  • Every interface has several addresses — one link-local (fe80::/10, always present, never routed) plus global ones. Multiple addresses per interface is normal, not an error.
  • Dual stack is the deployment reality: machines run IPv4 and IPv6 simultaneously and "Happy Eyeballs" (RFC 8305) races both, using whichever connects first. IPv6 did not replace IPv4 on a flag day; it grew alongside it.

Your laptop can reach the Internet. The Internet cannot reach your laptop.

You start a server on your laptop on the Karyashala WiFi. Your phone, on mobile data, cannot open it. This is not a bug. It is the network working exactly as designed — and understanding why is the whole point.

Four reasons the connection fails

  1. The address is not unique. 192.168.1.10 is private (section 06). There are millions of machines with that exact address. The phone's carrier has no idea which one you mean — and every router on the path drops RFC 1918 destinations rather than guess.
  2. NAT is stateful and one-directional. The Karyashala router builds a translation entry only when an inside machine sends something out (section 09). An unsolicited packet arriving from outside matches no entry, so the router has nothing to translate it to and discards it.
  3. No inbound port mapping. Even addressing the router's public IP, 49.207.198.45:8000, gets you nowhere: the router has not been told that port 8000 belongs to the laptop.
  4. You may not even own a public IP. Many Indian broadband and all mobile connections use carrier-grade NAT (100.64.0.0/10). Your router's "public" address is itself private to the ISP, and port forwarding is impossible no matter what you configure.
The asymmetry, stated plainly

NAT lets connections out and blocks connections in. Everything you do on the web works because you initiate. The moment you want to be the one who is contacted, the model breaks — and you need either a port forward, a public server, or a tunnel.

Tunneling: make the outbound direction do the work

A tunnel exploits the one thing that does work — outbound connections. The trick:

1. An agent on your laptop opens an outbound TLS connection to a public edge server. 2. NAT happily allows it and creates a translation entry — this is a normal outgoing flow. 3. The edge server assigns you a public hostname, e.g. https://a1b2c3.ngrok-free.app 4. Your phone requests that hostname over the public Internet. It resolves to the edge server. 5. The edge pushes the request back down the connection you already opened. 6. The agent forwards it to localhost:8000, gets a response, and sends it back up the same pipe. The tunnel is never "opened from outside". It is a door you propped open from the inside.

NAT: sixty devices, one public address, zero confusion

All of AI Karyashala shares a single public IP. Sixty students open codekaryashala.com:8000 at once, and the server sees sixty requests from the same address. Every single response comes back to the right laptop. How?

The answer in one line

The router does not track machines. It tracks conversations — and it identifies each one by rewriting the source port to a value it has never used before.

The five-tuple

Every TCP/UDP connection on Earth is identified by five values: protocol, source IP, source port, destination IP, destination port. Change any one of them and it is a different conversation. NAT rewrites the source IP (which it must, since private addresses cannot travel) and the source port (which it may, and which is what makes the whole thing work). Strictly this is NAPT — Network Address and Port Translation — and it is what every home and office router actually does.

So: how does the router know which machine?

Three facts, in order:

  1. Only the destination port is available. Everything else in the returning packet is identical for all three students — same public IP, and for the sixty students hitting codekaryashala.com the same server address too. The destination port is the one field that differs.
  2. The router made that port unique on purpose. When it created the entry it picked a translated port not currently in use for that destination. So port ⇒ exactly one row.
  3. The row holds the answer. Row 3 says 60003 ⇒ 192.168.1.12:51514. The router rewrites the destination and forwards it onto the LAN — using ARP to find that machine's MAC address (section 13).

And this is why sixty students works exactly as well as three: sixty rows, sixty distinct translated ports, sixty unambiguous return paths. The server at codekaryashala.com sees sixty connections from 49.207.198.45 and cannot distinguish the students at all — which is also why per-IP rate limiting punishes an entire classroom for one person's script.

Can you see other people's packets? Mostly no — and the reasons are the lesson

WiFi is radio. Your laptop's antenna physically receives every frame in the room. So why can't you read them?

Scope

This section is about understanding your own network, debugging your own traffic, and network administration on networks you are responsible for. Capture your own traffic, or traffic on a lab network set up for the purpose, with permission. Intercepting other people's communications is a criminal offence under the IT Act in India and equivalent laws elsewhere.

WiFi: shared medium, private keys

Two separate facts get confused here, and separating them is the whole section.

  • Reception is shared. Radio does not do point-to-point. Every device in range receives every frame at the physical layer. Normally the network card checks the destination MAC address and discards anything not addressed to it. In monitor mode it stops discarding and hands you everything.
  • Readability is not shared. On WPA2-PSK, everyone types the same password — but that password only produces the Pairwise Master Key. Each client then runs a four-way handshake with the AP, mixing in random nonces from both sides to derive a Pairwise Transient Key unique to that client's session. Unicast frames are encrypted with the PTK. You have the password, you still don't have your neighbour's PTK.

Your home "WiFi router" is all four devices in one plastic box — AP, switch, router, NAT gateway — which is exactly why the roles blur. The college pulls them apart into separate hardware, and suddenly each one's job is visible.

Why VLANs, and not just one big flat network

You could put all 3,000 devices on 10.10.0.0/16. You should not:

  • Broadcast containment. ARP and DHCP are broadcast. On a flat network every one of those reaches all 3,000 devices, and every device's CPU wakes up to ignore it. VLANs cut the broadcast domain down to one classroom.
  • Isolation. Classroom A cannot reach classroom B's machines unless the core switch is configured to allow it. Lab equipment, staff machines, CCTV, and student WiFi can each be a separate VLAN with its own policy.
  • Diagnosis. "Classroom B has no Internet" localises instantly to VLAN 20 — one subnet, one gateway, one DHCP scope.
  • Physical layout stops mattering. VLANs are logical. A staff laptop in classroom C can be on the staff VLAN while sitting next to a student on the student VLAN, on the same switch.

DHCP: how the laptop gets 192.168.1.10 without anyone typing it

You open your laptop, join the WiFi, and it works. Between "joined" and "works" are four messages — and the first one has to be shouted, because the laptop has no address to speak from yet.

The bootstrapping problem

A device joining the Karyashala network knows nothing: not its own IP, not the router's IP, not the DNS server, not even whether a DHCP server exists. It cannot send a unicast packet, because unicast requires knowing a destination. So the first message is a broadcast — 255.255.255.255, the address from section 06 that means "everyone on this link" — sent from source 0.0.0.0, the address meaning "I don't have one yet".

The subnet mask is a bitwise AND. That's the whole idea.

1 · What the mask means

The mask is 32 bits: a run of 1s followed by a run of 0s, never mixed. The 1s mark which bits of the address identify the network; the 0s mark which bits identify the host.

255.255.255.0 in binary
  255      .255      .255      .0
  11111111 .11111111 .11111111 .00000000
  └──────── 24 ones ─────────┘ └─ 8 zeros ─┘
     network part                host part

  24 network bits  →  written as /24
   8 host bits     →  2⁸ = 256 addresses, 254 usable (section 06)

Applying it to your own address gives the network ID:

That is the operator from section 02, applied to 32 bits instead of 8. Nothing else is happening.

2 · How the machine decides "same network or not"

AND the destination with the same mask. Compare the two results. Equal ⇒ local. Different ⇒ remote.

3 · Destination is local — deliver it directly

Take 192.168.1.20. Both AND to 192.168.1.0, so it is on this link. No router is involved at all:

1. Check the ARP cache for 192.168.1.20. Not there. 2. Broadcast ARP: "Who has 192.168.1.20? Tell 192.168.1.25" → every device on the link hears it 3. Reply: "192.168.1.20 is at b8:27:eb:44:12:aa" → only that machine answers 4. Build the frame: dst MAC = b8:27:eb:44:12:aa dst IP = 192.168.1.20 5. The switch/AP delivers it. One hop. TTL is not decremented — no router touched it.

This is why two students on the same WiFi can reach each other's dev servers directly (section 08), and why ARP is visible to everyone in a capture (section 10).

4 · Destination is remote — hand it to the gateway

Take 8.8.8.8. AND gives 8.8.8.0 ≠ 192.168.1.0. Remote. Now the crucial move:

1. Not local → send it to the default gateway, 192.168.1.1 2. ARP for the gateway's MAC — not for 8.8.8.8. You cannot ARP for something that is not on your link; ARP is a broadcast and broadcasts do not leave the link. 3. Build the frame: dst MAC = 3c:84:6a:11:02:f0 ← the ROUTER's MAC dst IP = 8.8.8.8 ← the FINAL destination, unchanged 4. Router receives it, sees the IP is not its own, consults its routing table, rewrites the MAC addresses for the next hop, decrements TTL, forwards.
The single most important idea in this section

The MAC address changes at every hop. The destination IP address never changes. The IP is the final destination — end-to-end. The MAC is only "the next device to hand this to" — hop-by-hop, rewritten by every router along the way. A packet crossing eight routers has eight different destination MAC addresses and one destination IP throughout. Hold on to this; section 17 is nothing but this sentence repeated across continents.

5 · Why the gateway is needed at all

Your laptop's routing table has two entries and neither of them knows anything about the Internet:

ip route — the entire local worldview
ip route
default via 192.168.1.1 dev wlan0           ← everything I don't recognise
192.168.1.0/24 dev wlan0 scope link          ← my own neighbourhood

Longest-prefix match: a destination of 192.168.1.20 matches the /24 (more specific) and is delivered locally. A destination of 8.8.8.8 matches only default — which is 0.0.0.0/0, a mask of zero bits, matching literally everything. The gateway is the answer to "I don't know where this goes, you deal with it." Your laptop needs to know about exactly one network and one router. That delegation is what makes the Internet scale: no machine holds a map of the whole thing.

CDN: move the content closer, because you can't move the speed of light

Light in fibre travels about 200,000 km per second. Visakhapatnam to Virginia and back is roughly 28,000 km of cable. That is 140 ms of pure physics, before a single server does any work. No amount of optimisation removes it.

The problem, measured

*TCP handshake (1 RTT) + TLS handshake (1–2 RTT) + request/response (1 RTT). Latency is multiplied, not added — this is why distance hurts far more than raw bandwidth.

What a CDN is

A network of cache servers — edge PoPs, points of presence — placed in dozens or hundreds of cities. A user's request is steered to the nearest one. If that edge has the content, it answers immediately. If not, it fetches once from the origin, keeps a copy, and answers everyone else locally.

WITHOUT a CDN — 500 students in Vizag load the site 500 requests ──────── 14,000 km ────────→ origin in Virginia 500 responses ←─────── 220 ms each ─────── Origin serves 500× the same logo. Every user waits 220 ms per round trip. WITH a CDN student 1 ──→ edge, Hyderabad MISS ──→ origin, Virginia once, 220 ms │ caches it students 2–500 ─→ edge, Hyderabad HIT 15 ms each Origin served 1 request. 499 users got a 15 ms response.

How the request finds the nearest edge

Two mechanisms, often combined — and both are just section 16 and section 17 being used cleverly:

  • DNS steering. The CDN runs the authoritative nameserver and returns a different IP depending on where the query came from. A resolver in Andhra Pradesh gets the Hyderabad edge; one in Berlin gets Frankfurt. Same hostname, different answer.
  • Anycast. The same IP address is advertised via BGP from every PoP simultaneously. Ordinary Internet routing then delivers each packet to whichever PoP is closest in network terms. Cloudflare's 1.1.1.1 works this way — it is one address and hundreds of machines.

The five benefits, and the mechanism behind each

The trade-off nobody mentions in the sales pitch

Caching means staleness. You fix a typo, deploy, and the old text is still live at 200 edges until the TTL expires or you issue a purge. A CDN also becomes another party that terminates your TLS and can see your traffic, and another dependency that can fail. A CDN outage takes down sites that were themselves perfectly healthy.

DNS: turning aikaryashala.com into four bytes

You type a name. The network only understands numbers. Between the two is a distributed database with no single owner, queried billions of times a second, that answers in about 30 milliseconds.

The eight caches and servers, in order

Every step exists to avoid the next one. The whole design is layered caching.

Recursive vs authoritative — the distinction that unlocks the rest

An authoritative server knows the truth for its own zone and nothing else. It answers only about names it owns, and for anything else it says "ask over there". A recursive resolver knows nothing but is willing to do the legwork: it chases referrals from root to TLD to authoritative on your behalf and hands you one final answer. Your laptop asks one question and gets one answer; the resolver asked three questions to produce it.

The classic operational mistake: change the IP first, then think about the TTL. By that point resolvers worldwide have already cached the old answer for 24 hours and there is nothing you can do. Lower the TTL a day before you migrate, move, then raise it again.

Things that will bite you

  • Negative caching. A "no such name" answer is cached too, governed by the SOA record's minimum field. Create a record and it can still 404 for minutes.
  • DNS is UDP port 53 and falls back to TCP for large answers. A firewall blocking TCP/53 breaks DNSSEC and big responses in ways that look random.
  • Plaintext by default — which is why an observer sees your lookups (section 10). DoH and DoT encrypt them to the resolver, though the resolver still knows everything.
  • CNAME chains cost round trips. Each alias is another lookup. CDNs use them heavily, which is why a first page load has more DNS latency than you'd expect.
  • The resolver's location decides your CDN edge (section 14). Using 8.8.8.8 from Vizag can land you on a worse edge than using your ISP's resolver. EDNS Client Subnet exists to fix this by passing along a truncated client address.

Routing: nobody knows the whole path

There is no map of the Internet anywhere. No router knows the route to your destination. Each one knows only the next step — and that is enough.

The journey

Student laptop 192.168.1.25 knows: my subnet, my gateway. Nothing else. ↓ §13 — not local, so send to the gateway Karyashala WiFi router 192.168.1.1 / 49.207.198.45 ↓ §09 — NAT rewrites source, records the row ACT Fiber access CGNAT and aggregation ↓ ISP core network ACT's own backbone, AS 24309 ↓ BGP decides which neighbour AS to hand it to Internet backbone / IXPs peering and transit between networks ↓ Destination network the AS that owns the destination prefix ↓ Destination server the final hop, delivered locally

What each router actually does — five steps, every hop

  1. Receive the frame and check the destination MAC is mine. Strip the Ethernet header.
  2. Read the destination IP. Not mine ⇒ this needs forwarding.
  3. Longest-prefix match against the routing table. Among all matching entries, the most specific prefix wins.
  4. Decrement TTL. If it hits zero, drop the packet and send back ICMP Time Exceeded — which is what traceroute harvests (section 15).
  5. Build a new frame with the next hop's MAC address and send it. The destination IP is untouched.
Section 13's rule, at global scale

The destination IP never changes. The MAC address changes at every single hop. A packet from Vizag to Virginia has one destination IP for its entire life and perhaps twenty different destination MAC addresses along the way. The IP is the address on the envelope; the MAC is which postal worker you hand it to next.

Same algorithm at every scale. Your laptop, the Karyashala router, and a backbone router carrying a million routes all do exactly this. Only the table size differs.

Autonomous Systems and BGP

An Autonomous System is one network under one administrative policy, with an AS number. ACT is one. Google is one. A large college can be one. There are roughly 75,000 active AS numbers in the world — and that is the number the global routing system has to cope with, not the billions of individual addresses.

TermMeaning

BGP chooses by policy, not by distance

BGP does not pick the shortest or fastest path. It picks according to business relationships: prefer routes learned from customers (they pay you), then peers (free), then transit providers (you pay them) — and only then compare AS path length. This is why a packet from Vizag to Chennai occasionally routes through Singapore. The physics is not the constraint; the contracts are.

It is also why BGP is fragile. It runs largely on trust: if a network advertises a prefix it does not own, others may believe it. This has taken down large parts of the Internet by accident more than once. RPKI is the ongoing effort to add cryptographic verification of who may announce what.

Visakhapatnam → Amalapuram: every idea, in one packet

The path

How ACT knows where to send it

Three cases, and the first one is the common one for a nearby destination:

  1. The server is inside ACT's own network. ACT's interior routing protocol (OSPF or IS-IS) already carries the route. The packet never leaves AS24309 — Vizag to Vijayawada to Amalapuram on ACT's own fibre. Around 8–12 hops, 15–25 ms. Nothing external is consulted at all.
  2. The server is on another Indian ISP. ACT's border router has learned that prefix over BGP from a neighbour. If ACT peers directly with that ISP — likely at NIXI Hyderabad or Chennai — the packet crosses at the exchange and comes straight back into Andhra Pradesh. One AS hop, still fast.
  3. No peering exists. ACT hands the packet to a transit provider (Tata, Airtel, Bharti), who has a route. This is the case where a Vizag→Amalapuram packet may physically travel to Chennai or Mumbai and back — 180 km of geography, 2,000 km of cable, because the contracts route it that way, not the map (section 17).

And how did ACT learn the route in the first place? The destination network advertised it. "AS64500 can reach 103.x.y.0/24" propagated across BGP sessions, each AS prepending itself to the path, until ACT's border router held an entry saying for this prefix, hand the packet to this neighbour. ACT never learns the full path — only the next AS. Section 17's rule holds all the way down.

Back to the first byte

Follow the thread all the way down and every networking idea on this page turns out to be section 01 wearing different clothes:

  • An IPv4 address is four bytes — the N-byte rule from section 05 with N = 4. That is why there are 2³² of them, why we ran out, and why NAT and IPv6 both exist.
  • A subnet mask is a bitwise AND — the operator from section 02, applied to 32 bits. Longest-prefix match is the same comparison, done many times and sorted by how many 1-bits matched.
  • A port is two bytes — so 65,536 of them, which is the hard ceiling on how many conversations one NAT public address can carry.
  • A MAC address is six bytes — 2⁴⁸ addresses, enough that manufacturers never need to reuse one.
  • TTL is one byte — starting at 64 or 128, which is why traceroute tops out around 30 hops and why no packet can circle forever.
  • Every one of those bytes is a pattern of transistors, switching in NAND configurations, at the bottom of section 03.
The one sentence for the whiteboard

A computer is bits given meaning by agreement — a byte is a number because the type says so, an address is a location because the routing table says so, a port is a conversation because the NAT table says so. Every layer of this page is one more agreement about what a pattern of bits is allowed to mean. Nothing else changed between section 01 and section 18.
