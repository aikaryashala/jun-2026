# Build a Mini HTML Parser — Questions

These questions have **no single right answer**. They are about **your** work: what you did, what you decided, and what you learnt. Write your answers **in your notebook**, in your own words.

Answer them **as you go**, not only at the end — a question you answer after Phase 3 will get a different (and more honest) answer than one you answer after Phase 8 from memory.

Before you start, try the **Quiz** for this task to check your basic understanding.

---

## Part A — Reflect on the process

1. Before you wrote any code, what did you think the hardest part of this program would be? After finishing, what actually was?

2. Pick **one** prompt you gave OpenCode that worked well and **one** that did not. Write both down. What made the difference?

3. Describe one time the AI generated code that was **wrong** or **poor**. How did you find out — a test, a run, reading the code, or something else?

4. Name **two** design decisions that were **yours**, not the AI's. Why did you decide that way?

5. Did splitting the work into phases change what the AI produced? What do you think would have happened if you had asked for the whole parser in one prompt?

6. Pick one commit. What can you learn about it from Git alone? What more did Entire show you about the same commit?

7. Was there a moment you **accepted** AI code without fully understanding it? What did you do about it later?

8. How did you check that a test written by the AI expected the **right** answer?

9. What did building the parser **twice** — in C, then in Python — teach you that building it once would not have?

10. Six months from now, another student must continue your project. Apart from the code, what would they need to know? Where would they find it?

11. Is source code alone a complete record of how software was built when an AI agent helped write it? Why, or why not?

12. **The big question.** If an AI coding agent can generate a large portion of the source code, what becomes **more** important for a software engineer? Think about: understanding the problem, design, breaking work into steps, asking good questions, verifying, testing, debugging, reviewing AI output, making decisions, and preserving context.

## Part B — Your Final README

Answer these in your notebook first. Then turn your answers into the `README.md` of each repository.

1. **What you built.** What does your program do? How does someone build it, run it, and run its tests?

2. **How OpenCode was used.** In which phases did you use it, and for what kinds of tasks — understanding, design, code, tests, debugging, review?

3. **How Entire was used.** What did it record? When did you look at what it recorded, and what did you find there?

4. **Important prompts and decisions.** Which prompts and which decisions shaped the program the most?

5. **Bugs you encountered.** List the bugs. For each: how did it show up, how did you find the cause, and how did you fix it?

6. **C versus Python.** What was different between the two implementations — in design, in effort, in the kinds of bugs?

7. **What would be lost.** If we kept only the final source code and the Git commits, what information about your work would be gone?

> Do not complete everything in one step. Work incrementally and keep the development process visible.
